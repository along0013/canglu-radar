# 舱路雷达项目风险记录 v1

> 记录日期：2026-07-01  
> 范围：基于当前 `canglu-radar` 项目结构、README、engine、dashboard、output/data、archive 归档材料的检查结果。  
> 用途：作为后续项目优化、工程化复跑、前台产品化设计的风险基线。

---

## 1. 总体判断

当前 `canglu-radar` 已具备阶段性交付能力：包括 V5 架构文档、数据格式规范、计算引擎、Dashboard、输出 JSON、归档交付包和自检材料。

但项目当前更接近“已完成交付态 + 保留引擎代码”，而不是一个完全开箱即跑、可长期维护的工程化系统。主要风险集中在：

- 复跑入口不清晰；
- 原始输入与结果输出边界混淆；
- Dashboard 数据契约未完全锁定；
- 归档包与当前工程主线关系需要明确；
- 前台化后对趋势解释、异常发现、数据质量提示的要求会显著提高。

---

## 2. P0 风险

### P0-1：默认复跑链路不通顺

**现象**

直接执行默认命令时会遇到路径问题：

```bash
$BOX_AGENT_PYTHON engine/validate.py
$BOX_AGENT_PYTHON engine/compute.py --check-only
```

当前项目没有 `engine/data` 目录，而代码/配置默认路径与当前实际数据目录不完全一致。

**影响**

- 新人接手时无法按 README 快速复跑；
- 后续优化前台时，难以稳定生成最新数据；
- 每次交付可能依赖人工记忆路径，增加不可控风险；
- 一旦数据更新，可能出现“看板展示旧数据”的问题。

**建议**

- 明确标准输入目录，例如：`data/raw/`；
- 明确标准输出目录，例如：`output/data/`；
- 修正 `config.yaml` 与 README 中的默认路径；
- 增加一键命令，例如：

```bash
./scripts/run-validate.sh
./scripts/run-compute.sh
./scripts/build-dashboard-data.sh
```

或 Makefile：

```bash
make validate
make compute
make dashboard-data
make package
```

---

### P0-2：输入数据与输出数据边界混淆

**现象**

当前存在多类数据目录：

- `archive/01-raw-data/`：历史原始材料；
- `output/data/`：当前 Dashboard 可用 JSON 结果；
- `engine/data/`：代码默认期待但当前不存在。

**影响**

- 难以判断哪个目录是权威数据源；
- 难以追踪结果 JSON 对应哪批原始数据；
- 不利于前台做数据更新时间、数据血缘、数据质量提示；
- 对后续自动化任务、定时计算、版本回溯不友好。

**建议**

建立明确数据分层：

```text
data/raw/             原始输入
data/processed/       清洗后中间数据
output/data/           前台/报告消费的标准结果
archive/               历史交付与证据链
```

并在输出 JSON 中加入元信息：

```json
{
  "meta": {
    "data_version": "2026-W27",
    "generated_at": "2026-07-01T10:00:00+08:00",
    "source_batch": "raw-2026-w27",
    "engine_version": "v5"
  }
}
```

## 3. P1 风险

### P1-1：Dashboard 数据契约未完全统一

**现象**

当前 `output/data/` 中存在：

- `metrics.json`
- `decisions.json`
- `dashboard-metrics.json`
- `dashboard-decisions.json`

从命名看，可能同时存在标准引擎输出与 Dashboard 适配输出。

**影响**

- 前端不知道应该以哪组数据为准；
- 字段变更时容易导致 Dashboard 空白或展示错误；
- 不利于后续做交互式前台、筛选、详情页和问题解释。

**建议**

明确文件职责：

| 文件 | 定位 | 消费方 |
|---|---|---|
| `metrics.json` | 标准指标输出 | API / 分析 / 报告 |
| `decisions.json` | 标准决策输出 | API / 分析 / 报告 |
| `dashboard-metrics.json` | 前端视图模型 | Dashboard |
| `dashboard-decisions.json` | 前端视图模型 | Dashboard |

同时在 `specs/data-format-v5.md` 中补充“文件级契约”，并让 `validate.py` 覆盖 Dashboard 所需字段。

---

### P1-2：前台化后解释性不足

**现象**

当前系统已有指标和建议，但如果直接做成图表，用户可能仍然不知道：

- 为什么这条航线风险升高？
- 是价格、舱位、延误、拥堵还是船司公告导致？
- 建议动作背后的根因链是什么？
- 这个建议的置信度是多少？

**影响**

- 使用者只能看到结果，不能建立信任；
- 业务人员仍需二次人工判断；
- 管理层难以追踪系统建议是否有效。

**建议**

每个异常或建议都应补充：

- 风险等级；
- 触发因子；
- 根因链；
- 影响范围；
- 建议动作；
- 置信度；
- 证据来源；
- 最近一次更新时间。

---

### P1-3：归档包与当前工程主线关系不清晰

**现象**

`archive/08-submission/final-package/` 中存在最终包、自检报告和 manifest。但如果当前工程继续迭代，需要明确归档包是历史快照还是当前最新交付。

**影响**

- 后续修改 engine/dashboard 后，final-package 可能滞后；
- 项目交付版本难以追踪；
- 复盘时难以知道某次报告对应哪版代码和哪批数据。

**建议**

建立版本元信息：

```text
release_id: canglu-radar-v5-20260701
engine_version: v5
schema_version: v5.0
data_batch: 2026-W27
package_created_at: 2026-07-01
```

并提供可重复生成最终包的命令。

## 4. P2 风险

### P2-1：缺少前端运行时验收

**现象**

当前 Dashboard 是静态 HTML，主要依赖 JSON 文件。如果字段或路径变更，页面可能无法正确展示。

**影响**

- 代码层校验通过，但页面层可能失败；
- 前台化后交互复杂度提升，问题更隐蔽。

**建议**

增加轻量 smoke test：

- 检查 Dashboard 引用的 JSON 是否存在；
- 检查核心 DOM 节点是否存在；
- 检查 JSON 字段是否被页面消费；
- 条件允许时做浏览器截图验收。

---

### P2-2：缺少用户视角的信息架构

**现象**

当前系统从工程角度看较完整，但前台产品化需要重新围绕用户任务组织信息。

**影响**

如果只是把后台指标图表化，用户仍可能难以完成核心任务：

- 今天哪些航线需要关注？
- 哪些问题正在恶化？
- 我应该提前订舱、分批发货还是延迟？
- 哪些判断是高置信，哪些需要人工确认？

**建议**

前台应以任务链路设计：

```text
总览态势 → 发现异常 → 解释原因 → 给出动作 → 记录反馈 → 复盘效果
```

而不是仅按数据表或指标堆叠。

---

## 5. 后续优化优先级

### 第一优先级：工程可复跑

- 修正默认路径；
- 补标准输入目录；
- 增加一键运行脚本；
- 输出数据加入 meta 信息。

### 第二优先级：数据契约统一

- 明确标准输出与 Dashboard 输出关系；
- 完善 schema 文档；
- 增强 validate.py；
- 固化字段版本。

### 第三优先级：前台产品化

- 设计用户任务流；
- 增加趋势、异常、根因、建议动作、置信度展示；
- 增加筛选、钻取、对比、收藏/标记、反馈闭环；
- 增加数据质量和更新时间提示。

### 第四优先级：交付自动化

- 自动生成 final-package；
- 自动生成 manifest；
- 自动生成自检报告；
- 支持版本回溯。

---

## 6. 结论

当前项目的主要矛盾不是“有没有产出”，而是“能否稳定复跑、解释清楚、持续迭代”。

如果后续要把后台运算做成交互式前台，建议先解决 P0 的路径和数据边界问题，再围绕用户任务链路设计前台。否则前端越丰富，底层数据不稳定带来的信任风险越大。
